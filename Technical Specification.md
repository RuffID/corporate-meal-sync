# Техническое описание обмена СКД → iikoCard → 1С

Назначение и бизнес-логика проекта описаны в [README.md](README.md).
Здесь приведены настройка, форматы данных, запуск и обработка ошибок.

Все адреса, учётные данные, ID и карты в примерах вымышленные. Они согласованы
с `app/main/config.example.json` и не подходят для рабочего подключения.
Сумма 100 ₽ приведена только как пример; рабочую сумму задаёт `config.local.json`.

## Сценарии

| Точка запуска | Действие | Дата по умолчанию |
| --- | --- | --- |
| `app/main/skdtoiiko.py` или `app/skdtoiiko.bat` | Скачать CSV с SFTP и выполнить начисления | Сегодня |
| `app/main/loadwithoutftp.py` или `app/skdtoiikowithoutftp.bat` | Обработать CSV, полученный вручную | Сегодня |
| `app/main/iikoto1c.py` или `app/iikoto1c.bat` | Получить списания, сформировать CSV и отправить на SFTP | Вчера |
| `app/main/sync.py` | Общая консоль: импорт, экспорт, отчёт, фиксация ручной сверки | Зависит от команды |
| `app/main/gui.py` | Графический интерфейс над той же логикой | Выбирается в интерфейсе |

В GUI сохранены загрузка карт, выгрузка за сегодня/выбранный день и отчёт за период.
Добавлена загрузка локального CSV. Сетевые операции выполняются в рабочем потоке;
пока он работает, кнопки заблокированы и окно нельзя закрыть.

Дата «сегодня» определяется системными часами компьютера, на котором запускается
скрипт. Для повторной обработки конкретного дня явно задавайте `--date YYYY-MM-DD`.
Вчерашняя консольная выгрузка и выгрузка за сегодня в GUI — разные сценарии.

недостаточно. `State` необходимо сохранять и резервировать вместе с рабочими данными.

## Установка и настройки

Код использует синтаксис Python 3.9. Для новой установки рекомендуется поддерживаемая
версия Python, например 3.11 или новее. Системные установщики не входят в Git.

Из корня проекта:

```powershell
python -m pip install -r requirements.txt
# Если нужен графический интерфейс:
python -m pip install -r requirements-gui.txt
```

В новой копии проекта создайте `app/main/config.local.json` по образцу
`config.example.json`. Все значения подключения в примере вымышленные: замените
их рабочими параметрами в локальном файле. Не переносите рабочие настройки
в пример или исходники.

Основные поля (значения ниже совпадают с примером конфигурации):

| Поле | Назначение |
| --- | --- |
| `api_url` | HTTPS-адрес iikoCard API, пример `https://iikocard.example.invalid:9900` |
| `api_login`, `api_password` | Учётные данные интеграции; пример `example-login` / `example-api-password` |
| `organization_id` | Организация; пример `11111111-1111-4111-8111-111111111111` |
| `program_id` | Программа питания; пример `22222222-2222-4222-8222-222222222222` |
| `wallet_id` | Кошелёк; пример `33333333-3333-4333-8333-333333333333` |
| `category_id` | Категория; пример `44444444-4444-4444-8444-444444444444` |
| `refill_amount` | Положительная сумма пополнения с точностью до копеек; пример `100` |
| `timeout_seconds` | Таймаут HTTP и SFTP, от 1 до 300 секунд |
| `data_dir` | Папка данных; относительный путь считается от файла конфигурации |
| `sftp_host`, `sftp_port` | SFTP-сервер и порт, пример `sftp.example.invalid:2202` |
| `sftp_username`, `sftp_password` | Учётные данные SFTP; пример `example-sftp-user` / `example-sftp-password` |
| `sftp_remote_dir` | Папка обмена на сервере, пример `Exchange` |
| `known_hosts_file` | Путь к необязательному файлу проверенных SSH-ключей; относительно конфигурации |

Можно выбрать другой файл параметром `--config` или переменной окружения
`WATER_SYNC_CONFIG`. Для общего журнала обычный и ручной импорт должны использовать
одну папку данных, организацию и кошелёк.

### Ключ SFTP-сервера

Файл `known_hosts` необязателен. Если его нет, ключ сервера принимается автоматически,
как в старой версии. Подлинность сервера в этом режиме не проверяется, а полученный
ключ не сохраняется на диск. Для подключения используются логин и пароль из конфигурации.

Если файл существует, проверка ключа включается: ошибка чтения файла, неизвестный
сервер или несовпадение ключа останавливают обмен. Для подготовки файла получите
публичный ключ и его SHA256-отпечаток у администратора сервера, проверьте соответствие
и сохраните подтверждённую строку в `app/main/known_hosts`.
Для нестандартного порта имя узла в строке — `[sftp.example.invalid]:2202`.
Строка имеет вид `[host]:port тип-ключа ключ-в-base64`.
Одна лишь загрузка ключа из сети не подтверждает подлинность сервера.

Исходящий CSV передаётся обычной командой SFTP `put` сразу под итоговым именем,
как в старой версии. Поддержка дополнительных расширений сервера не требуется.
После передачи проверяется размер файла. Уже существующий файл заменяется.
При обрыве передачи на сервере может остаться частичный файл; локальный CSV
сохраняется для повторной отправки. Получатель должен читать файл после завершения передачи.

## Форматы файлов

### Входящий `YYYYMMDD-SKD-IIKO.csv`

Одна строка — один пропуск из 16 шестнадцатеричных символов. Кодировка UTF-8,
допускается BOM. Пробелы удаляются, регистр приводится к верхнему; хвостовые нулевые
символы `\u0000` считаются заполнением фиксированной строки и удаляются.
Нулевые символы в середине и лишние символы не исправляются догадками.

Пример преобразования:

```text
Пропуск:                       AA00000000002A01
Срез Python [8:14]:             00002A
Число HEX → DEC:                42
Трек с дополнением до 10 цифр:  0000000042
```

До запросов на изменение проверяются все строки. Строки с неправильной длиной
или не-HEX символами пропускаются с записью файла, номера строки и значения в лог.
Повтор одного пропуска пропускается, первое вхождение обрабатывается один раз.
Если разные пропуска дают один трек, исключаются все спорные строки, а остальные
карты обрабатываются. Пустой файл, ошибка чтения и неверная кодировка останавливают
импорт. Если все непустые строки отклонены, итог содержит ноль начислений и число
пропущенных записей.
Прежнее замечание о строках длиной 20/22 символа и совпадающем срезе остаётся
вопросом к формату СКД: обрезать такие идентификаторы до первых 16 символов нельзя.

### Исходящий `YYYYMMDD-IIKO-1C.csv`

UTF-8 без BOM, разделитель `;`, дробная часть суммы через запятую:

```text
PassID;TransactionDate;TransactionSumm
AA00000000002A01;2030-01-15;12,50
```

Используется `corporate_nutrition_report` за выбранный день. В файл входят только
строки с `payFromWalletSum > 0`. Если таких строк нет, файл не создаётся и на SFTP
ничего не отправляется; ранее созданный файл за этот день не используется вместо
пустого отчёта. Некорректный ответ или сумма не трактуются как нулевые списания.
CSV записывается через временный файл, поэтому ошибка не оставляет частичный результат.

## Проверка гостя и защита начислений

1. CSV полностью проверяется до изменений в iiko. Основной и ручной импорт получают
   общую блокировку, поэтому не могут одновременно начислять деньги.
2. Гость ищется по вычисленному номеру карты через API. Его имя не используется
   для выбора среди дублей. Проверяются ID, `isDeleted=false`, `isBlocked=false`
   и ровно одна активная карта с ожидаемым `Track`.
   Удалённый, заблокированный гость, неактивная или неоднозначная карта пропускаются
   с причиной в логе; остальные карты продолжают обрабатываться. Некорректная
   структура ответа API остаётся ошибкой всего сценария.
3. Кеш `guests.verified.json` хранит только проверенные соответствия. Если кеш
   указывает на действующего другого гостя, карта пропускается и нужна ручная сверка. Подтверждённый
   удалённый кешированный дубль можно заменить действующим владельцем карты.
   Ошибки кеша не исправляются молча. Старый `guests.json` не читается новой версией:
   он мог содержать обрезанное имя или неверный трек.
4. Только конкретный ответ `HTTP 400 / Card_CanNotFindByNumber` считается отсутствием
   карты. Другая ошибка 400, 401, 404, таймаут или неверный JSON не разрешают создать
   нового гостя. После `create_or_update` возвращённый гость проверяется заново.
5. Категория назначается только при её отсутствии. Уже имеющаяся действующая
   категория не назначается повторно; неактивная или дублированная категория
   приводит к пропуску карты с записью причины в лог.
   Если нужный кошелёк отсутствует, выполняется включение в программу питания,
   затем появление кошелька проверяется повторным чтением гостя.
6. Для существующих гостей до начислений проверяется отчёт транзакций за день.
   Чужое положительное пополнение без маркера этой операции требует сверки.
   Это осторожная проверка: отчёт не даёт надёжного wallet ID для каждой строки,
   поэтому нельзя автоматически признать чужое пополнение нужной выплатой.
7. Перед POST пополнения на диск атомарно записывается состояние `sending`.
   В комментарий операции передаётся маркер из организации, кошелька, даты и карты.
   После HTTP 200 сохраняется `confirmed`. При ошибке сохраняется `unknown`.
8. Подтверждённая операция при перезапуске пропускается. Неизвестная операция
   автоматически подтверждается только при единственной транзакции с тем же маркером
   и суммой. Пустой отчёт не разрешает повторный POST. Два совпадения требуют разбора.

Журнал защищает одну выплату на карту, дату, организацию и кошелёк. Изменение CSV
или суммы не превращает повторный запуск в новую выплату. Ошибки отдельных карт
логируются и не останавливают импорт. Ошибки сети, API, журнала или финансовой
сверки останавливают сценарий с ненулевым кодом; уже подтверждённые начисления
не откатываются. Проблема гостя не отменяет сверку неизвестного начисления.
Глобального отката через API нет. Часть проверки и изменений остаётся последовательной,
поэтому сбой сети всё ещё может привести к частичной обработке.

Это не серверная гарантия exactly-once: в описанном API пополнения нет ключа
идемпотентности. Нельзя удалять журнал, автоматически повторять финансовые POST
или запускать две независимые копии с разными папками `State`.

## Запуск из корня проекта

```powershell
# Обычный импорт за сегодня:
python app/main/sync.py import-sftp

# Если актуальный CSV получен вручную и лежит в app/main/Csv:
python app/main/sync.py import-local --date 2030-01-15

# Выгрузка вчерашних списаний:
python app/main/sync.py export

# Выгрузка выбранного дня:
python app/main/sync.py export --date 2030-01-15

# Чтение отчёта: обе указанные даты включены в период:
python app/main/sync.py report --from 2030-01-01 --to 2030-01-15

# Графический интерфейс:
python app/main/gui.py
```

Существующие BAT-файлы сохранены: они используют `%~dp0` и передают параметры дальше.
Код выхода 0 означает завершение сценария, 1 — ошибку выполнения, 2 — ошибку параметров.
При пропуске отдельных карт импорт завершается с кодом 0; в итоговой строке лога
и в GUI отдельно указаны начисления, уже подтверждённые выплаты и пропуски из-за ошибок.
Тестовые режимы не имитируют запуск рабочего импорта.

### Первый запуск после старой версии и неизвестный результат

Новая версия не знает, какие выплаты старая версия уже сделала. До обработки ранее
загруженного дня сверяйте реальные операции iiko. Старая версия могла выполнить
повторные или ручные пополнения. Новая версия не отменяет такие начисления.

Если желаемая выплата уже выполнена и подтверждена оператором, отметьте её локально:

```powershell
python app/main/sync.py resolve-refill --date 2030-01-15 --card AA00000000002A01 --guest-id 55555555-5555-4555-8555-555555555555 --result applied --reason "Выплата 100 рублей сверена в iiko"
```

Если после проверки установлено, что именно желаемая выплата не выполнена:

```powershell
python app/main/sync.py resolve-refill --date 2030-01-15 --card AA00000000002A01 --guest-id 55555555-5555-4555-8555-555555555555 --result not-applied --reason "Проверены операции: желаемое начисление отсутствует"
```

Эти команды меняют только локальный журнал, не вызывают API и не начисляют деньги.
Причина обязательна и сохраняется в истории. `not-applied` разрешает новый запрос
при следующем импорте; применять её по одному лишь таймауту нельзя.
Подтверждённую выплату нельзя снять командой `not-applied`.

## Диагностика

Новые логи: `app/main/Logs/YYYY-MM-DD_<сценарий>.log`, UTF-8 с временем и уровнем.
HTTP-ошибки содержат метод, путь, статус, код ошибки и тело ответа. Пароли и токены
удаляются из сообщений и traceback. Необходимые данные гостей остаются локальными.

| Проблема | Что делать |
| --- | --- |
| CSV не появился автоматически | Проверить этап SFTP и имя файла на сервере. Факт формирования у отправителя не доказывает доставку на SFTP |
| DNS/соединение не работает | Проверять сеть на рабочем компьютере; вручную подложенный CSV обходит только SFTP, но не доступ к iikoCard |
| Некорректная строка или коллизия трека | Записи пропускаются с причиной в логе; исправить выгрузку СКД, не обрезать идентификаторы догадками |
| Гость удалён, заблокирован или карта не совпадает | Карта пропускается с причиной в логе; сверить действующего владельца в iikoCard |
| Неактивная или дублированная категория | Карта пропускается; проверить категорию гостя в iikoCard |
| Категория уже есть | Новая версия пропускает повторное назначение |
| `sending` / `unknown` или чужое пополнение | Сверить транзакции; затем выполнить `resolve-refill` с реальным результатом |
| Другой процесс держит блокировку | Дождаться его завершения; ОС освобождает блокировку при аварии, удалять файл не требуется |
| Ошибка проверки ключа SFTP | Если `known_hosts` существует, сверить его записи с администратором; отсутствие файла включает автоматическое принятие ключа |
| Ошибка выгрузки на SFTP | Локальный CSV сохранён; проверить соединение и права на запись. На сервере возможен частичный файл |

### Почему добавлена проверка категории

В прежней версии импорт останавливался на HTTP 400 при назначении категории.
Проверка состояния через API показала действующего гостя с активной картой
и уже назначенной категорией. Удалённые дубли существовали, но ID из ошибки
принадлежал действующему гостю. Выбор удалённого дубля не подтвердился.
Повторное назначение категории осталось вероятной причиной: старые логи
не сохраняли тело ответа, поэтому точную причину восстановить нельзя.

Новая версия проверяет гостя и категорию до изменений, пропускает уже действующую
категорию и сохраняет тело новых HTTP-ошибок с удалением секретов.

## Проверки разработки

Изолированный набор использует временные файлы и подставной клиент. Случайный реальный
HTTP-вызов проваливает тест. GUI, приложение, SFTP и рабочие начисления не запускаются.

```powershell
python -m unittest discover -s tests -p "test_*.py" -v
```

Проверяются дубли и NUL-заполнение, продолжение импорта после плохих строк и гостей,
статусы гостей и карт, повторное назначение категории,
неизвестный результат POST, восстановление по маркеру, ручная сверка, блокировка,
повреждение журнала, контракты CSV/API, скрытие секретов и сохранение прежнего файла
при ошибке передачи. Синтаксис рабочих исходников проверяется на совместимость с Python 3.9.
Эти тесты не доказывают работу новой версии на реальном iikoCard, SFTP и в GUI.

## Git и локальные данные

В Git должны храниться рабочие исходники, пример конфигурации с вымышленными
значениями, зависимости, BAT-файлы, тесты и оба документа.

CSV, логи, кеши гостей, журнал начислений, секреты, ключи, установщики, папки
`restore` и `.vs` исключены. `.vs` содержит локальные файлы Visual Studio,
включая TestStore, `.testlog`, `testlog.manifest` и `slnx.sqlite`.
Старые инструкции и версии могут храниться внутри локального архива
`restore/pre-refactor-*`; рабочее описание состоит из README и этого документа.
Отдельное исключение `.gitignore` не удаляет данные с диска и не заменяет их резервирование.

Документацию iikoCard API используйте из официального источника, доступного вашей
организации. Для этой интеграции нужны методы работы с гостями, категориями,
корпоративным питанием, кошельками и отчётами транзакций.
